# ForecastBench entry v1: the rules (goes with prereg addendum 7)

These are the human-readable rules behind `prereg/v1.addendum-7-forecastbench.json`. That addendum fingerprints
the exact files and constants listed at the end. `--submit` refuses unless all of these hold:

- the addendum is committed, stamped (`.ots`) and matches the code;
- exactly one commit ever touched the addendum (changes are new versions, never edits), and that commit is before
  00:00 UTC on the due date (the `.ots` is not time-checked: `ots upgrade` legitimately rewrites it);
- nothing under `src`, `config`, `uv.lock` or `pyproject.toml` differs from the commit it was built from, and
  `git status` shows nothing there either, so no untracked module can shadow the fingerprinted code.

Any change needs a new, stamped addendum before the next counted round; `--dry-run` never needs one. Whether a
checked file is then uploaded also depends on the operator hold (section 7a), which never changes a forecast.

Code: `src/firm/forecast/contests/forecastbench.py` (the run), `fb_dataset.py` (dataset model), `fb_market.py`
(anchor aging), `fb_sources.py` (free inputs), `forecastbench_addendum.py` (the fingerprint and its check).
Settings: `config/forecastbench.yaml`, `config/forecastbench_calibration.json`. Exploratory evidence:
`research/forecastbench_dataset_backtest.md` (not part of the addendum).

## 1. What we send each round

| file | organization / model_organization | model | what it is |
|---|---|---|---|
| `{date}.lens-ledger.1.json` | Lens & Ledger | `ensemble v1` | named entry: AI + market anchor, statistical dataset model |
| `{date}.anonymous-154.2.json` | Anonymous 154 | `stats baseline v1` | control: aged anchor alone, same dataset model, no AI |

- Names are public and permanent; chosen under Spiro's brief (`decisions/2026-11-18-forecastbench-entry.md`).
  "ensemble" follows FRI's rule for entries that combine models. The anonymous name must not reveal us (the file
  check refuses "lens" or "ledger" in it).
- Two files a round (FRI allows three; only one may carry our name). `reasoning` is `null` everywhere.
- Main minus baseline is what the AI adds over plain statistics. Both entries are logged in our normal decision
  feeds under their own contest names (`forecastbench`, `forecastbench_baseline`), so our site counts both and a
  loss of the AI entry to the baseline gets published.

## 2. Timing

- A launchd job (`ops/launchd/pinned/com.lensledger.forecastbench.plist`, run under `caffeinate -i -s` so the Mac
  stays awake) fires daily at 08:10 Perth = 00:10 UTC and exits at once unless today (UTC) is a due date: every 14
  days from 2026-11-22.
- On a due date: wait for `{date}-llm.json` on FRI's GitHub until 06:00 UTC (checks every 2 minutes); run the
  named entry, then the baseline; each is checked and uploaded on its own. The AI stops at 20:00 UTC (the rest:
  anchor alone); no upload starts after 23:30 UTC (deadline 23:59:59 UTC). Expected finish: a few hours after the
  file appears, so there is a large buffer.
- One run at a time (a lock file, for both entries).

## 3. The question file

- The set is accepted only if it is this round's (`forecast_due_date` and `question_set` match). A malformed single
  question (bad id or source, a duplicate, invalid resolution dates) is skipped and logged rather than sinking the
  round; its forecasts count as missing in the coverage check below.
- A copy of the file and its sha256 go into the private store; it embeds exchange prices and is never committed.

## 4. Market questions (no resolution dates: Kalshi, Polymarket, Metaculus)

The existing contest forecaster, unchanged: the `pipeline.py` pieces and `prompts/forecast_v1.md` with the settings
of addendum 1 and the misread guard of addendum 2 (both files are byte-identical and fingerprinted here).

1. **Anchor.** The question's own `freeze_datetime_value` (a market price, or Metaculus' community forecast),
   taken 10 days before the due date. Using it is Spiro's decision of 2026-11-18. `N/A`, missing or outside [0, 1]
   means no anchor. Our own collected Kalshi/Polymarket data and live prices are never used.
2. **Aged anchor** for markets closing within 50 days of the due date:
   `logit(p) = a + (b + c z) logit(freeze)`, `z = 1 / (1 + days to close / 14)`, fitted on the run day on every
   published past round's resolved markets (FRI's files only; questions FRI nullified are left out). Settled
   anchors (0 or 1) and markets closing later keep the raw value, so the anchor can jump at the 50-day cutoff. The
   AI is shown the raw freeze value with its date; the aged value is what the blend and the misread guard use.
3. **AI view.** Sonnet 5.5 (`forecast` role), effort medium, up to 16,000 tokens, the frozen system prompt, JSON
   outcomes `Yes` / `No`. Headlines: free Google News RSS for the last 14 days (GDELT as fallback), items after the
   decision time dropped. The user message gives today's date, the question, close time, source, background and
   rules (each cut to 2,500 characters), the anchor labelled "market chance on <freeze date>, 10 days before
   today's due date", and the headlines. A refused or unusable answer counts as no AI view.
4. **Misread guard** (addendum 2). An anchor of exactly 0 or 1 is a known result (AI ignored). If the AI is more
   than 50 points from the anchor, its view is dropped for that question.
5. **Blend.** `sigmoid(0.2 * logit(AI) + 0.8 * logit(anchor))`. With no anchor, the AI view alone; with no AI view,
   the anchor alone; with neither, 0.5. Then the pipeline's finalize for a Yes/No pair (clipped to [0.005, 0.995]).
6. **Settled check.** Runs only when Sonnet is at least 90% sure and at least 25 points from the anchor, and there
   are headlines. It is a cheap routine-model call (Haiku 5.5, thinking off, `contests/prompts/fb_settled_v1.md`,
   about $0.0003). It counts only if it names a headline published after the freeze **and** Sonnet already agrees
   the same way; then the forecast is 0.97 (or 0.03). This is the only way past the misread guard. (A market whose
   close date has passed is no reason to check: FRI nullifies markets that close or resolve on or before the due
   date.)
7. **Order and budget.** Markets are forecast soonest-closing first (unknown close dates last), because markets
   closing within 50 days are most of what is scored first. The named entry is capped at **$5 per round** in code,
   counting every run for that round (a re-run cannot spend the cap again), inside the usual monthly caps. The
   estimate is printed before any spend. Realistic cost: $4.60-5.60 for 250 questions (about $0.02 a call, with
   occasional long answers up to $0.16), so the cap may bind around question 200; the rest, the furthest-off
   markets, use the anchor alone. A re-run reuses AI views already logged for the round.
8. **Baseline entry:** the aged anchor clipped to [0.005, 0.995] (0.5 without one). No AI.
9. **Not used:** aging every market's anchor (it lost in the backtest), a cheaper model for far-off markets, and
   several samples per question (they do not fit the cap).

## 5. Dataset questions (resolution dates: ACLED, DBnomics, FRED, SerpApi, yfinance)

No AI; cost $0. The same forecasts go into both entries: they are computed once per question set and model, and
cached for the second entry only when nothing fell back to a default.

Each question asks whether a value on each resolution date will be strictly higher than on the due date (ties
resolve No). For ACLED it asks whether a 30-day event count will beat a past 30-day average. Rules by type:

- **FRED and DBnomics (ECB) series.** Data comes free on the day from FRED `fredgraph.csv` and the DBnomics API.
  - Over the last year of the series, how often was the value h days later strictly higher? Only days whose
    previous h-day move had the same sign as the latest move count. Shrink toward 0.5 (10 pseudo-windows).
  - "Value on a date" is the latest observation dated on or before it. With the due date a Sunday, daily series
    compare with Friday. This rule reproduces all 8,178 past FRED/DBnomics resolutions.
  - FRI's templates for these sources only ask "increased" / "exceed", so the direction is always "higher". Words
    inside series names such as "below investment grade" never flip it.
  - One year of history cannot measure 365-day moves, so that horizon uses the learned rate.
- **ACLED** (no ACLED data is fetched): the learned rate for questions with a similar 30-day average (the
  question's freeze value), shrunk toward a Poisson chance, mixed with the same question's own past results (the
  rate counts as 16 such results).
- **SerpApi flight delays:** the share of the 14 days listed in the question that were above their median, mixed
  with the learned rate.
- **SerpApi shop prices:**
  - Learned rate per horizon, with a prior of 0.15 for "strictly higher": prices are mostly unchanged, and
    unchanged resolves No.
  - The prior was set after seeing tie rates, so it is not blind. Published results outweigh it within a few rounds.
  - **Calendar rule, stated before the 2026-11-22 round (reasoning only, not backtested, not blind):** for an
    Amazon resolution date from Black Friday to Cyber Monday (27-30 Nov 2026; our 7-day checkpoint is 29 Nov), the
    forecast is multiplied by 0.6, because those days are in the sales.
  - Walmart grocery prices and flight delays get no holiday rule.
- **yfinance stock pairs** (no Yahoo data): 0.5 by symmetry, never calibrated. Single-stock questions (retired) used
  a drift rule.
- **Anything else** (including new sources): the learned rate for its type and horizon, mixed with its own past
  results; 0.5 when nothing is known.
- **Learned rates:**
  - Learned from past ForecastBench question sets joined with their published resolution sets, using only results
    published before the due date. Each past round counts as at most 10 observations per type.
  - A horizon with no results yet borrows the nearest horizon that has some, pulled toward 0.5 the longer it is:
    `0.5 + (r - 0.5) * nearest / h`. With no results at all, the type's prior is read as a 30-day rate. So no
    365-day forecast copies a 7-day rate.
  - **This long-horizon rule is a judgement, not backtested.** In the reviewer's check it made the training Brier
    on dropped, stable question types worse (0.175 to 0.182). It is kept because today's types have no
    long-horizon results yet, and copying a 7-day rate to 365 days is the bigger risk.
- **Calibration:**
  - `logit(p') = a + b * logit(p)` per question type and horizon, from `config/forecastbench_calibration.json`.
  - It is written by the backtest from walk-forward forecasts of past rounds.
  - Groups need at least 50 forecasts from 5 rounds; b is kept in [0.5, 2] and a in [-1, 1].
  - In practice ACLED is pulled a little toward 50%, and FRED is pushed outward and toward Yes at 7-180 days.
- Every forecast is clipped to [0.005, 0.995]. Any failure falls back to the learned rate, then to 0.5.

Note: SerpApi questions are Amazon and Walmart prices and flight departure delays, not Google Trends.

## 6. Checks before any upload (all must pass, or nothing is uploaded)

The file is written atomically, read back from disk and checked. The checks are a superset of FRI's own, in
`resolve/_prepare.py` and `leaderboard/main.py`:

- exactly the five top-level keys, with text values;
- organization, model and model_organization exactly as configured;
- `question_set` equals the question set's name, `{date}-llm.json`;
- every forecast has exactly `id, source, forecast, resolution_date, reasoning`, with text ids and sources and a
  text-or-null date;
- every (id, source, resolution date) is in the question set, and none appears twice (FRI halts scoring a round on
  duplicate dataset rows);
- each type has at least 98% coverage, counting skipped malformed questions as missing (FRI drops a file under 95%);
- every value is a finite number in [0, 1], and `reasoning` is null;
- the file name is `{date}.lens-ledger.1.json` or `{date}.anonymous-154.{1,2,3}.json` and matches the entry.

## 7. Upload

`gcloud storage cp FILE gs://forecastbench-submissions-prod-submissions/70642dcc/binary/{date}/` (bucket and folder
in config). Our folder is create-only.

- `--submit` works only on the due date itself (UTC), only with confirmed model names, only with a valid stamped
  addendum 7, and never after 23:30 UTC.
- An immutable copy of the checked bytes is made, and its sha256 is checked against them before every attempt.
- The same bytes are retried up to 3 times (waits of 30 s and 2 min); each attempt is recorded.
- On a final failure an `ops/errors` row is written (task `forecastbench.upload`); `firm.ops.health` lists these
  once installed. FRI accepts the file by email before the deadline as a fallback.
- The bytes uploaded are exactly the bytes that were checked (passed through, not re-read).

## 7a. Operator hold

**An operator hold can withhold submission; it never changes forecasts.**

- The switch is a file in the data folder, outside the code and the fingerprint, so it can be flipped without
  re-stamping: `~/lens-ledger-data/state/forecastbench_hold.json`, for example
  `{"hold": true, "reason": "Kalshi Legal reviewing", "decision": "decisions/2026-11-18-kalshi-pause.md"}`.
- **Fail closed:** a missing or unreadable file, or anything but an explicit `{"hold": false}`, means hold.
- While held, `--submit` and `--scheduled` still make both files and log every forecast privately (marked
  `held`, counted like a dry run, so the public site does not count them as entered). Then they refuse to upload
  with the reason "operator hold", write one `ops/errors` row of kind `held` per entry, and exit with code 2. The
  file is read again just before the upload, so a hold set during the run still stops it.
- Lifting the hold for a round: write `{"hold": false, "decision": "<record quoting Spiro>"}` and re-run
  `--submit`. Logged AI views are reused, so nothing is paid twice.
- A round and entry already attempted is never uploaded again unless `--force-reupload` is given after checking
  with FRI.
- Every forecast is in the decisions log before the upload.

## 8. Data terms

The question sets (CC BY-SA 4.0, FRI) embed Kalshi and Polymarket prices as freeze values. Using them in the entry
is Spiro's decision of 2026-11-18. The files stay in the private store (`~/lens-ledger-data/forecastbench`, raw
source `forecastbench`), and are never committed or published. Tests use made-up questions. The research note holds
aggregate scores only.
